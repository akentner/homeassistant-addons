## Symptoms

**Expected behavior:** avahi-daemon in the `cups` add-on settles on the configured hostname (`cups`) and stays there; mDNS resolution of `cups.local` (and the printer's `_ipp._tcp` service) succeeds reliably, so iOS AirPrint can select and use the printer.

**Actual behavior:** avahi-daemon inside `app_72a005f5_cups` is stuck in an active RFC 6762 probe-conflict rename loop, observed climbing from `cups-4` to `cups-13` within ~15 seconds of a fresh restart, never settling. `docker exec app_72a005f5_cups pgrep -a avahi-daemon` shows it perpetually in `avahi-daemon: registering [cups-N.local]` state. Simultaneously, the completely separate `network-tools` add-on (`app_72a005f5_network-tools`, different hostname scheme, no shared code with cups) is ALSO stuck in the same kind of loop, observed at `network-tools-175` after only ~1 hour uptime. Both `avahi-browse -rpt _ipp._tcp` and `avahi-resolve-host-name -4 <name>.local` (tried against cups.local, cups-2.local, cups-3.local, cups-4.local — every historically observed name) return "Timeout reached" — actual mDNS resolution is fully broken right now, not just cosmetically renamed.

**User-visible symptom (this is what surfaced the regression):** on iOS, selecting the AirPrint printer appears to fetch info, then silently deselects; after a longer wait iOS shows "Der Drucker ist offline" (the printer is offline).

**Error messages:** No explicit error text captured yet from avahi's own stdout (avahi-daemon is daemonized via `avahi-daemon --daemonize`, so its own conflict/rename log lines do not appear in `docker logs` — this needs checking via syslog or a foreground run). `docker logs app_72a005f5_cups` shows a clean boot sequence with no errors: cupsd starts, printer registers, the stable-UUID two-phase-boot fixup runs successfully, cupsd restarts cleanly. The rename loop is invisible in the container's captured stdout entirely.

**Timeline:** This exact class of bug (hostname-rename loop) was originally diagnosed and fixed earlier in this same GSD phase (21-cups-print-server-addon-airprint-mdns-fixes) via `cups/generate_config.py`'s `detect_primary_interface()` + `allow-interfaces=<iface>` scoping in `avahi-daemon.conf`, and was confirmed working for an extended period afterward (multiple successful restarts, stable UUIDs observed, real AirPrint print tests succeeded, including duplex). It reappeared today, noticed via the iOS "printer offline" symptom above, after a sequence of same-day quick-task deployments (AirPrint print-presets feature added/redesigned twice, then a stable-printer-UUID two-phase-boot feature, then presets removal in progress) — but network-tools being independently affected argues AGAINST those cups-specific code changes being the cause.

**Reproduction:** `ssh haos-op3050-1 "ha apps restart 72a005f5_cups"`, wait ~15s, then `ssh haos-op3050-1 "docker exec app_72a005f5_cups pgrep -a avahi-daemon"` — reliably shows a `cups-N` name with N already > 1, climbing further on repeated checks. `ha multicast restart` (restarting the `hassio_multicast` mdns-repeater service) was already tried as a mitigation attempt and did NOT stop the loop — cups climbed to `cups-13` on the very next restart afterward.

## Resolution

root_cause: "network-tools's avahi-daemon (started unconditionally by run.sh with zero avahi-daemon.conf customization, so it publishes address/reverse-PTR records by default) and cups's avahi-daemon both run under host_network: true, so they share the exact same host IPv4/IPv6 addresses. Each publishes a conflicting reverse-PTR record for those shared addresses under its own hostname, causing RFC 6762 probe-conflict rename storms on BOTH sides simultaneously and indefinitely -- confirmed directly via avahi's own foreground --debug log naming network-tools's hostname as the conflicting record's source."
fix: "Ship network-tools/avahi-daemon.conf with `[publish]\\npublish-addresses=no`, and COPY it to /etc/avahi/avahi-daemon.conf in network-tools/Dockerfile. This stops network-tools's avahi-daemon from registering any address/reverse-PTR record for the shared host-network addresses -- eliminating it from the conflict with cups's avahi-daemon entirely -- while leaving avahi-browse (used by mdns_scan.py for the mdns_monitors feature) fully functional. Version bumped config.yaml/build.yaml/README.md to 0.5.0-3 (add-on-only fix, upstream unchanged) via internal/update-version.py; CHANGELOG.md entry added."

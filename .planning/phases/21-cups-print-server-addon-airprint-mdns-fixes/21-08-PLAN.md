<objective>
Remove the observed cause of the lost fixed host name: our own local test containers announced `cups.local` on the real
LAN. Diagnosis (strongly indicated, confirmed by timing; final confirmation is the quiet observation in plan 21-10):
`journalctl --user` on the dev workstation shows podman creating and starting the Phase 22 verifier image
(internal/verify-cups-paperless-upload.sh) at 09:14:55; the live host logged `Host name conflict, retrying with cups-2`
at 09:14:57. That script's options.json fixtures set only `avahi_reflector`, so every container (happy, disabled, retry,
resilience) ran with the add-on default `avahi_hostname: "cups"` and announced `cups.local` -> workstation IPv4 through
podman's pasta networking, which reaches the real LAN (a passive mDNS capture saw a throwaway name announced by a
container). Against the live `cups.local` -> host IPv4 record that is a unique-record conflict, and the live avahi renames.
The other two verifiers use unique names (`cups-verify`, `cups-guard`), which explains why only some runs hurt, why the
restart-1 boot held 9.5 h overnight (no tests running) and why 21-04's post-restart watch saw no conflict. This corrects
the earlier reading "unknown foreign announcer" in 21-07-SUMMARY and 21-VERIFICATION (recorded by plan 21-09).

Purpose: make it structurally impossible for a local verifier to touch the live name again, and isolate test
containers from LAN mDNS altogether. Planning-time spike (podman 6.1.3, image built from cups/ at HEAD): with
`--cap-add NET_ADMIN` and `ip link set <iface> multicast off` run before `/run.sh` (as the CMD of the image's /init
entrypoint), avahi logs no "Joining mDNS multicast group" for the interface, still reports "Server startup complete.
Host name is <name>.local", the guard claims on attempt 1, cupsd's Listen is still rewritten to the interface address and
unicast reachability of the host (host.docker.internal) is untouched. `--network none` was rejected: it breaks the
scaffold's Listen assertion and the paperless stub-server path.

No add-on code changes: cups/ is untouched, so no version bump and no image rebuild is triggered. Decisions D-07, D-10,
D-11, D-12 are the ones this protects; D-01..D-06, D-09 and D-13 are untouched.
Output: internal/cups-test-isolation.sh, converted verifiers, a hardening check that makes the rule enforceable.
</objective>

    - `CUPS_TEST_STAMP` (default: current epoch seconds) and `CUPS_TEST_MUTE_SNIPPET`, a POSIX sh fragment that loops
      over every entry of /sys/class/net except `lo` and runs `ip link set <iface> multicast off`. The variable must be
      overridable from the environment with the `${VAR-default}` form so the RED proof can set it to a no-op (`:`); that
      override is a documented test-only knob.
    - `cups_test_hostname TAG`: prints `cups-vf-<TAG>-<STAMP>`; TAG must match `[a-z0-9-]{1,20}`; the result is at most 63
      characters and can never equal `cups`.
    - an internal check `_cups_test_check_data_mount` that scans the docker-run option words for the `-v SRC:/data` /
      `--volume SRC:/data` / `--volume=SRC:/data` mount, requires SRC/options.json to exist and to hold a JSON string
      `avahi_hostname` that is non-empty and not exactly `cups` (a syntactically invalid value is allowed: run.sh refuses
      to start on it before avahi exists, which is what the `refuse` scenario relies on), and otherwise prints
      `ERROR: refusing to start a cups test container: <reason>` to stderr and returns 2 without calling docker. A missing
      /data mount is also refused (no options.json means the default name `cups`). Parse the JSON with python3 -c.
    - `cups_isolated_run IMAGE [DOCKER_RUN_OPTIONS...]`: runs the check, then `docker run --cap-add NET_ADMIN
      <options> IMAGE sh -c "<MUTE_SNIPPET>; exec /run.sh"` (the CMD override keeps the image's /init entrypoint).
    - `cups_isolated_bash IMAGE SCRIPT [DOCKER_RUN_OPTIONS...]`: same check, then `docker run --cap-add NET_ADMIN
      --entrypoint bash <options> IMAGE -c "<MUTE_SNIPPET>; <SCRIPT>"` for the guard verifier's harness containers.
    - `cups_lan_run IMAGE [DOCKER_RUN_OPTIONS...]`: same check but NO isolation, documented as allowed only where a
      scenario must see mDNS on a real interface (the isolation negative control here, service-resolution scenarios
      later); it still enforces the unique-name rule and announces that unique throwaway name on the LAN for the
      container's lifetime.
    - all three call one internal docker-run wrapper that prefixes `timeout "$CUPS_TEST_TIMEOUT"` when that variable is
      set (a shell function cannot be run under `timeout`, so the helper owns it).

  <context>
    D-03 rates the printers list schema "costly" to change later — once real installs have `printers` entries typed
    into `options.json`, changing the field's schema type is a breaking change users must re-enter. CUPS device URIs
    use non-HTTP schemes this repo has never validated before: `ipp://`, `ipps://`, `socket://`, `usb://`,
    `dnssd://`, `lpd://`. The only existing precedent in this repo (`phone-logger/config.yaml`'s `output_webhooks[].url`)
    uses HA's built-in `url` schema type, but that field only ever holds `http(s)` webhook endpoints — whether HA's
    `url` validator (voluptuous `vol.Url`) accepts these printer-specific schemes is unverified.
  </context>
  <options>
    <option id="str">
      <name>`str` (permissive) + explicit runtime scheme-allowlist validation in generate_config.py</name>
      <pros>Guaranteed to accept every real CUPS URI scheme this add-on exists to support — no lock-out risk.
      Validation logic lives in one Python function and can be extended (new scheme) with zero config.yaml/schema
      change, so it never re-triggers the D-03 migration cost. Invalid entries are skipped + logged instead of
      crashing lpadmin.</pros>
      <cons>HA's Options UI gives no live format feedback while typing — a malformed URI is only caught at
      container start (surfaced clearly in add-on logs).</cons>
    </option>
    <option id="url">
      <name>`url` (HA's built-in URL schema type)</name>
      <pros>Free built-in format validation, consistent with the one existing precedent in this repo
      (phone-logger).</pros>
      <cons>Unverified whether voluptuous's `vol.Url` accepts non-http schemes (`ipp://`, `socket://`, `usb://`,
      `dnssd://`, `lpd://`). If it rejects any of them, users cannot register that class of printer through the HA
      UI at all — locking out exactly the CUPS URI shapes this add-on exists to support — and fixing it later is
      itself the costly migration D-03 warned about.</cons>
    </option>
  </options>

    - If "url" is chosen, Task 2's action additionally requires empirically confirming (via the Task 2 docker
      smoke test) that an `ipp://` URI passes HA's config.yaml options-schema validation before relying on it
  </acceptance_criteria>
  <resume-signal>Select: str (recommended — no lock-out risk) or url</resume-signal>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| HA Supervisor Options UI -> generate_config.py / run.sh | Admin-configured but externally-supplied strings (`avahi_hostname`, `printers[].name`, `printers[].uri`) cross into a generated config file and subprocess argument construction |
| LAN mDNS peers -> avahi-daemon / cupsd | Any device on the local network can reach the container directly once `host_network: true` exposes the host's real interfaces |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-21-01 | Tampering (Injection) | generate_config.py (avahi-daemon.conf writer + lpadmin command builder) | high | mitigate | `avahi_hostname` validated against `^[A-Za-z0-9-]{1,63}$` before being written into `host-name=` (rejects newline-injection into the config file); `printers[].name` validated against the same pattern, `printers[].uri` scheme checked against an explicit allowlist; lpadmin invoked via a `shlex.quote()`-escaped argv list, never an interpolated shell string; invalid entries are skipped + logged, never passed through |
| T-21-02 | Denial of Service | avahi-daemon legacy-unicast reflector slot table | high | mitigate | `enable-reflector=no` is the shipped default (D-07) — this is the root cause fix cups/DIAGNOSIS.md documents; the option (`avahi_reflector`) still exists so a user can knowingly re-enable it |
| T-21-03 | Information Disclosure / Spoofing | CUPS web UI + IPP on port 631, reachable from the whole LAN via `host_network: true` | medium | accept | No CUPS admin authentication is configured — matches upstream `f1c878cb_cups` behavior and this repo's existing AUTH-07-style precedent (terraform-bridge/iac-runner also rely on network-layer ACL, not app-layer auth, at Phase-1 LAN-trust tier); documented as an accepted risk in cups/DOCS.md (Plan 21-02) |
| T-21-04 | Tampering (supply chain) | apk packages: cups, cups-filters, avahi, avahi-tools, dbus, python3 | low | accept | All official Alpine `main`/`community` packages baked into the pinned `ghcr.io/home-assistant/amd64-base:3.24` image; the npm/pip/cargo package-legitimacy gate is out of scope for apk installs |
</threat_model>

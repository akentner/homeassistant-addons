Close the MEASUREMENT half of the two failed 21-VERIFICATION truths before any fix is written: (#13) the add-on's Avahi
daemon must claim the fixed `avahi_hostname` and keep it across restarts/updates, and (#14) the printer's `_ipp._tcp`

the live host; a checkable, re-runnable verifier is the missing proof mechanism, and the diagnosis decides whether the
planned startup guard (21-05) is sufficient.

Spec-less probe fallback: visibly SKIPPED -- ad-hoc phase whose requirements are the CONTEXT.md decisions D-01..D-13;
no SPEC.md exists for this phase.

Planning-time live findings (read-only observations on haos-op3050-1, 2026-10-03; raw addresses deliberately omitted per
the DIAGNOSIS.md leak-review precedent, commit 3ba5bf8). They shape the verifier, so the executor must treat them as
hypotheses to confirm, not as settled facts:
1. Avahi's own log sink is dead. Inside the add-on container `/dev/log` is a symlink to `/run/systemd/journal/dev-log`,
   a path that does not exist there, and run.sh starts avahi daemonized (syslog logging). Every conflict/rename message
   avahi ever emitted was discarded -- this is why 21-VERIFICATION could not name the cause (fix lands in 21-05).
2. The published `_ipp._tcp` instance is named `Brother-MFC-7460DN @ cups` while the daemon runs as `cups-2.local`.
   That is consistent with cupsd registering its services under the first-proposed host name and never re-registering
   after avahi's rename -- a candidate mechanism for truth #14.
3. Three avahi publishers share the one host IP (the HAOS host itself, the `network-tools` add-on with
   `publish-addresses=no`, and `cups`). A reverse lookup of the host IP from a LAN client therefore returns the HAOS
   host's own name, not the add-on's: `avahi-resolve -a <host IP>` from a LAN client is NOT a valid D-11 assertion. The
   verifier asserts forward and service resolution and records reverse lookups as INFO only.
4. D-10 is not achieved on the live host: `use-ipv6=no` only disables IPv6 sockets; Avahi still publishes the host's
   IPv6 ULA as an AAAA record over IPv4 (`publish-aaaa-on-ipv4` defaults to yes), so `avahi-resolve-host-name -6
   cups-2.local` from a LAN client returns the ULA the original diagnosis complained about.
5. Timeline: cups and network-tools were started 19 seconds apart in the same Supervisor start wave on 2026-09-29, about
   six minutes after the host booted. A cold-start race between sibling avahi daemons is plausible but unproven.
</objective>

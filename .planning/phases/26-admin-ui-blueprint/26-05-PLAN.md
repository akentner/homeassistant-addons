<objective>
Build the optional Home Assistant integration modules of the lib: `color.mjs` (parsing, WCAG maths, serialisation),
`theme-sync.mjs` (read a whitelist of the parent theme's CSS variables, guard contrast, set `--sync-*` and `data-theme`)
and `ha-bridge.mjs` (the `home-assistant/*` postMessage protocol: properties store, narrow-driven kiosk policy, menu
button and navigate). Everything degrades silently to the own theme and the fixed layout (D-11, D-13).

Purpose: the user wants HA colours and layout facts used automatically, but the protocol is undocumented and without
stability promise (CONTEXT, research A3), so the modules are injectable, fully unit-tested with fake windows, and guarded
against every failure and hostile value. The live spike (plan 26-13) settles what stays guaranteed.

Output: three modules and three node test files.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Parent window (HA frontend) -> iframe via postMessage | inbound messages can come from any window that holds a reference; HA posts with target origin `*` |
| Iframe -> parent via postMessage | outbound messages cause HA to change layout (kiosk, navigation) |
| Parent DOM/CSS variables -> own CSS | theme values come from HA or a user-authored theme and end up in our stylesheet |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-26-20 | Spoofing | `ha-bridge` inbound handler | high | mitigate | accept only `event.source === win.parent` plus `event.origin === win.location.origin`, then validate every field; tests for foreign source, foreign origin, wrong type and malformed payloads |
| T-26-21 | Tampering | `ha-bridge` outbound `postMessage` | medium | mitigate | explicit target origin (page origin), `*` only when the origin is opaque; messages contain only fixed type strings and a validated path; no secrets ever sent |
| T-26-22 | Information disclosure | `theme-sync` parent access | medium | mitigate | read only the five whitelisted CSS variables from the parent, never storage, cookies or other DOM; all access in try/catch; raw strings are not stored in `status` |
| T-26-23 | Denial of service | kiosk re-subscribe, observer, poll | medium | mitigate | transitions only from received messages, sticky host-bar probe, freeze guard (more than 4 transitions in 10 s), 3 s poll, observer callbacks never throw |
| T-26-24 | Tampering (CSS injection) | `--sync-*` values | high | mitigate | values are parsed to numbers and re-serialised as `#rrggbb` or `rgba()` before `setProperty`; anything else is dropped; tests with hostile strings assert the written-value pattern |
| T-26-25 | Elevation of privilege | `navigate` message | low | mitigate | only a single-slash relative path, max 512 chars, no scheme or control characters; triggered only by explicit user actions (spike button) |
| T-26-SC | Tampering | package installs | high | accept | No package installs in this plan (standalone modules, Node built-in test runner) |
</threat_model>

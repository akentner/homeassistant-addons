<objective>
Build `internal/jobq`: the background execution engine behind `POST /v1/plan` and `POST /v1/apply`. It owns admission
control (global semaphore + per-repo mutex), the run lifecycle in the store, the tofu command lines, the timeout
kill-chain, the plan-artifact lifecycle, and live output capture.

Purpose: RUN-02, RUN-03 and RUN-06 are all execution-semantics requirements, and RUN-06's concurrency guarantee is the
single riskiest thing in this phase — "the mutex is released on job exit (success, failure, or crash recovery)" is easy to
get wrong and expensive to debug in production. Isolating it in a package with an injected exec function makes
serialization, capacity refusal and the timeout kill-chain provable in unit tests under `-race`, with no tofu binary and
no real repo involved.

Output: 5 new files. `cd iac-runner && go build ./... && go vet ./... && go test ./internal/jobq/... -race` all exit 0.

Requirements satisfied by this plan:

- RUN-02: `tofu init -input=false` then `tofu plan -no-color -out=/data/runs/{run_id}/plan.tfplan` as a background job
- RUN-03: `tofu apply -no-color -auto-approve [planfile]` as a background job
- RUN-06: same-repo applies serialize via an in-process per-repo mutex, cross-repo applies run in parallel, and the mutex
  is released on every exit path

Locked decisions implemented here:

- D-04: `max_parallel_jobs` as a buffered-channel semaphore wrapping the per-repo mutex map
- D-05: per-repo mutex held in a lazily-populated map, in-process only (no cross-restart serialization)
- D-06: saturation is refused, not queued — the HTTP layer turns it into 503 + `Retry-After: 30`
- D-15: `apply_timeout_minutes` becomes a context deadline on the tofu process
- D-16: SIGTERM at expiry, SIGKILL 10s later, run marked failed with `apply_timeout`, slots released via defer
- D-17: apply with no usable prior plan runs inline `tofu apply -no-color -auto-approve`
- D-18: apply with a prior successful plan for the same (repo, dir) consumes that plan file, falling back to inline when
  retention already swept it

Explicitly OUT of scope: HTTP handlers and status codes (17-06), option parsing and construction (17-07), a cancel
endpoint (deferred per CONTEXT), cross-restart mutex persistence (explicitly deferred per CONTEXT).
</objective>

    // background and is the only place in the runner that starts a
    // process on behalf of an HTTP request.
    //
    // Two independent admission gates, per CONTEXT D-04..D-06:

    //   1. A global semaphore of max_parallel_jobs slots, acquired

    //

    //

    defer func() { <-q.sem }()                       // global slot, always

            // A panic in exec or in the store must not wedge the repo
            // mutex or leak a slot. Record the run as failed and let

            _, _ = q.store.Update(runID, func(m *runs.Meta) error { … status failed, error_code apply_failed … })

    lock.Lock()
    defer lock.Unlock()

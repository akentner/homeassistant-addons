<objective>
Land the two GitHub Actions workflows that gate every future Bridge/Provider release on CI: (1) `build-terraform-bridge.yml` reuses the Phase 8 reusable workflow template to build + push the Bridge image to GHCR on every push to `main` touching `terraform-bridge/**` and on every `terraform-bridge/v*` tag; (2) `test-terraform-provider.yml` runs `gofmt -l .` / `go vet ./...` / `go test ./...` against the Provider source with the same dual-trigger pattern. Also land `internal/verify-install-provider.sh`, the hermetic shell verifier that Plan 03's E2E workflow will invoke (and that the `make verify-install-provider` wrapper from Plan 01 already points at).

Purpose: the existing per-addon build workflows (`build-meridian.yml`, `build-network-tools.yml`, etc.) follow a thin
`uses: ./.github/workflows/_build-template.yml` pattern. Plan 02 ports that pattern to `terraform-bridge`, which is the
only v1.3 add-on whose Dockerfile is multi-stage Go (the template already accommodates this — Phase 9's 09-01 confirmed
`_build-template.yml` handles the `BUILD_FROM` / `VERSION` / `CONFIG_VERSION` yq extraction). For the Provider, there is
no equivalent build template (it's not an HA add-on), so `test-terraform-provider.yml` is a self-contained Go-ci
workflow.

Output: 3 new files — `.github/workflows/build-terraform-bridge.yml` (uses the reusable template),
`.github/workflows/test-terraform-provider.yml` (standalone Go CI), `internal/verify-install-provider.sh` (hermetic
test). Pre-push hook extension (`internal/check-version-tags.sh`) is in scope only as a verification: confirm the
existing hook auto-discovers `terraform-bridge/` correctly via the
`if [[ -f "$addon_dir/config.yaml" && -f "$addon_dir/build.yaml" ]]` test.

criteria 1, 2, 4 are non-requirement deliverables that this plan covers). Plan 03 covers success criterion 3 (E2E CI
verification). </objective>

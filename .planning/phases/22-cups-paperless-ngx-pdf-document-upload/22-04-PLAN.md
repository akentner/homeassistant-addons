<objective>
Close the single gap in 22-VERIFICATION.md (`status: gaps_found`, 17/18): truth 18, "a document is recorded as `sent/` only when paperless-ngx actually accepted the POST" (code-review finding CR-01). `upload_document()` in `cups/upload-worker.py` calls `requests.post()` with the default `allow_redirects=True` and treats any final 2xx as success. A 301/302/303 answer is turned into a GET on the `Location` target (SSO/login page, SPA index, API root behind a reverse proxy); if that target answers 2xx the worker logs "uploaded", deletes the sidecar and retry state and moves the PDF to `sent/` although paperless-ngx never received the document. No retry, no `failed/` routing, no WARNING: the D-15 visibility mechanism is bypassed. The verification run reproduced this against the real `upload_document()`.

What this plan delivers, derived from the gap's three `missing:` items:
1. Redirects are refused: `allow_redirects=False`, every 3xx is a failed attempt, and the `Location` target is logged (sanitized) so the operator can fix `url` (D-01 keeps `requests` multipart POST + Token auth; only the call's redirect handling and success classification change).
2. The success check is tightened to what the ROADMAP documents and the paperless-ngx source confirms (`PostDocumentView.post()` returns `Response(async_task.id)`, i.e. HTTP 200 with the task UUID as a bare JSON string): HTTP 200 and a non-empty JSON-string body.
3. Verification that cannot pass vacuously: a host-side probe that fails against the pre-fix worker, plus a redirect-stub Scenario 5 in the Docker verifier asserting retry -> `failed/` and no `sent/` entry.

Scope boundary (deliberate, visible): 22-VERIFICATION.md `advisory:` items (WR-01..WR-08, IN-01..IN-06 of 22-REVIEW.md) are not gaps (the verifier judged that none falsifies a declared truth) and are NOT planned here, per the gap-closure instruction to address only the `gaps:` block. They stay `open` in 22-REVIEW-DISPOSITION.md; only CR-01 changes state. `attempt_and_route()`, `process_new_document()`, `poll_once()` and every `generate_config.py` code path are untouched.

Purpose: make "sent" mean "paperless-ngx accepted the task" (ROADMAP Phase 22 design) under the plausible proxy/SSO/http-to-https deployments, and make a wrongly configured `url` surface through the existing D-15 WARNING instead of a silent false delivery.

Output: fixed `cups/upload-worker.py`, new host-side probe `internal/verify-cups-upload-worker.py`, extended `internal/verify-cups-paperless-upload.sh` (success-body shape + Scenario 5), corrected `cups/DOCS.md`, version bump `0.1.0-17`.

Planning notes (visible, not silent):
- Discovery level 0/1: only the already-present `requests` library and `urllib.parse` are used; the one external fact (paperless-ngx's response shape) was verified this run against the paperless-ngx API docs ("immediately return HTTP 200 ... with the UUID of the consumption task as the data") and the `PostDocumentView.post()` source (`return Response(async_task.id)`).
- Task 2 deliberately does NOT enforce a UUID pattern on the task id: the id format is a Celery implementation detail; requiring a non-empty JSON string is enough to reject login HTML, JSON objects and empty bodies, and avoids dead-lettering every document if the id format ever changes. Any such false negative stays visible (one D-15 WARNING) and never deletes a document (see T-22-12).
- Version bump runs with `NO_TAG=yes NO_PUSH=yes`: pushing a `cups/v...` tag triggers an image build, which is a release decision the operator makes (repo CLAUDE.md: ask first for version bumps/deployments). The SUMMARY must list the tag command as an operator follow-up.

- `COVERAGE.md` (paperless-ngx API surface matrix) is unaffected: no new endpoint or field is integrated.

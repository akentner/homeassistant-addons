  Documentation facts (must match the implementation in 24-06..24-09 exactly):
  1. Baseline is applied additively at every start through the CLI and never deletes anything. A baseline user is created
     when missing; an existing user's password is never changed. For an entry with a non-empty topic the rule `rw`
     (write_access true) or `ro` is set when no rule exists, and re-synced while the rule still has origin `options`;
     a rule created or edited in the GUI has origin `gui` and is left alone. An empty topic creates only the user.
     Entries removed from the options are not deleted; their origin becomes `gui` at the next start. A baseline entry that
     names `admin_user` is ignored with a warning.
  2. The admin from `admin_user`/`admin_password` is created only when missing; an empty `admin_password` skips creation
     with a log line; a password changed in the GUI is never overwritten.
  3. Guardrails: the last admin and the options-defined `admin_user` cannot be deleted or demoted; password change is
     allowed; deleting a user needs the user name typed as confirmation; promoting a user to admin drops their explicit
     rules (admins can do everything), they are stashed and restored on demotion, with a backup created first.
  4. Backups: `<data>/backups`, name `auth-<UTC timestamp>-<reason>.db`, one daily backup at start, a backup before user
     deletion, role changes that drop rules and every reset, rotation keeps the newest `backup_keep`, downloadable in the GUI;
     backups contain password hashes and clear-text tokens.
  5. Resets need typed phrases `reset acls`, `clear cache`, `reset everything`; each writes a backup first; "reset
     everything" removes all users and rules, then recreates the admin and baseline from the options and is refused
     while `admin_password` is empty; baseline ACLs return after "reset acls" at the next start.
  6. Tokens: the list never contains values; a value is revealed per row on demand (POST), a new token shows its value once
     at creation and can be revealed again; "last used" is approximate because ntfy updates it lazily; revoking passes the
     token as a command argument for a moment inside the container.
  7. Effective rights follow ntfy: admin role everything; otherwise the user's own matching rules beat rules for
     `everyone`, then the longest pattern, then write-capable first; no match falls back to `auth_default_access`;
     matching is case-sensitive (`pub*` does not match `PUB1`).
  8. Test publish creates a two-minute token for `admin_user`, publishes one real message and removes the token.
  9. Passwords reach the ntfy CLI only through the environment; secrets are never logged; the GUI answers only to the HA
     ingress proxy (peer 172.30.32.2 plus `X-Ingress-Path`), including static files and reads.

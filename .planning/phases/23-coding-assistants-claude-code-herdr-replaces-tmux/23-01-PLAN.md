<objective>
Ship Claude Code in the coding-assistants image next to opencode, with a persistence layout that keeps `claude update`
working across restarts and image rebuilds, persisted `~/.claude` state, a rewritten-on-every-start TOOLS.md block in
Claude's user-level CLAUDE.md (D-03), and optional auth through two password options. No settings, permission or model
defaults are added (D-04).

The first task is a tracer: it wires the thinnest end-to-end path (Dockerfile seed -> run.sh bootstrap -> running
container -> `claude --version` through the persistent launcher) and, in doing so, creates the phase's Docker verify
harness `internal/verify-coding-assistants.sh` with a stub Supervisor, so every later plan can prove its behaviour against
a real `run.sh` instead of reading code.

Purpose: Claude Code is the primary assistant of the user; this plan makes it a first-class, self-updating, persistent
citizen of the add-on.

Output: Dockerfile seed block, run.sh bootstrap/persistence/auth blocks, two new add-on options, harness scenarios
`claude-launcher`, `claude-state`, `claude-auth`.
</objective>

These user decisions were made AFTER the research and override conflicting literal text in CONTEXT.md / ROADMAP.md:

1. Claude persistence layout. The ROADMAP Phase 23 locked decision ("run.sh bootstraps it into /data/claude/bin and
   symlinks ~/.local/bin/claude") and the parenthetical in CONTEXT D-04 ("binary in /data/claude/bin") are REPLACED by:

   $XDG_DATA_HOME/claude/versions and leaves the launcher on the old binary; 23-RESEARCH.md Pattern 2, Pitfall 1). The

2. Default 7: a one-time copy of a legacy /data/claude/.claude and /data/claude/.claude.json into the new paths is
   trivial (copy-if-absent) and therefore included; nothing else is migrated and the old files are left on disk.
3. Default (research assumption A9): Claude is NOT version-pinned; the installer fetches the latest release at build time
   exactly like opencode, and the runtime updater keeps it current.
</user_decision_overrides>

<harness_facts>
Verified while planning (do not re-derive):
- The HA base image's bashio (Community Apps bashio) reads add-on options from the Supervisor API
  (`GET /addons/self/options/config`, response envelope `{"result":"ok","data":{...}}`), NOT from /data/options.json, and
  `bashio::addon.version` calls `GET /addons/self/info`. Without a Supervisor every `bashio::config` call prints "Something
  went wrong contacting the API" and returns an empty value. run.sh also reads /data/options.json directly with jq.
- bashio honours the environment variables `SUPERVISOR_API` (default `http://supervisor`) and `SUPERVISOR_TOKEN`.
- `with-contenv bashio` needs the image's own s6 `/init` entrypoint: start test containers with the image default
  ENTRYPOINT/CMD (never `--entrypoint bash`), as internal/cups-test-isolation.sh documents.
- Supervisor semantics: every add-on start is a NEW container on the same /data volume. The harness therefore models a
  "restart" as `docker rm -f` followed by a fresh `docker run` with the same /data bind mount, never `docker restart`
  (a restart would keep stale pid files and container-local state that production never sees).
</harness_facts>

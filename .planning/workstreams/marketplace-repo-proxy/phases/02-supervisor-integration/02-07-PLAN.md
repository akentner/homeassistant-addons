an approval checkpoint followed by one small `auto` task (one or two `ha` commands); human-action checkpoints cover the
steps only the user can do (HA UI edits, upstream push, merge/install). The executor returns at every checkpoint and a
fresh session continues, so no context window carries the whole run.

anything else. It re-reads the run state (`e2e.env`, `steps.log`) and the partial SUMMARY (`summary-draft.md`),

<resume>
Resume protocol: the first step of every session. The executor returns at every checkpoint and execute-phase spawns a
fresh agent for the next task, so this plan runs as many short sessions, and nothing from an earlier shell survives.
Every session (the first one, each continuation, and a fresh start after a crash) runs R1-R4 before anything else and
runs no host command before R4.

Run state lives only in `E2E_SCRATCH` = `$HOME/.local/state/mrp-e2e-02-07` (directory mode 0700, files mode 0600).
Shell variables do not persist between commands, so every command that needs a run state file spells out this path.

- `e2e.env`: run values as `key=value`, each key at most once (`choice`, `repo` as owner/repo, `addon`, `proxy_slug`, `store_slug`, `sync_interval`, `sub_install`, `restart_utc`, `push_utc`, `new_version`, `delete_utc`). A resumed step reuses an existing key and never appends a second line for it.
- `steps.log`: append-only, one line per event: `{UTC} task={N} event={confirmed|approved|aborted|skipped|started|done|failed}`. The session that receives a checkpoint answer logs it (`confirmed` for Task 1 and the human-action tasks, `approved`/`aborted`/`skipped` for approval checkpoints). An auto task appends `started` right before its first host command and `done` (or `failed`) only after its evidence block is written.
- `store-before.txt` (baseline slug list from step A), `needles` (Task 23), and `summary-draft.md`: the partial SUMMARY, a `Status: in progress` line and one `### Step {A-H}` block per step with masked evidence; a re-run step replaces its block and never adds a second one.
- In the tasks below, "scratch file" means `e2e.env` and `steps.log`, and "record for the SUMMARY" means writing that step's block in `summary-draft.md`.
- Never in any run state file: the GitHub token, an access hash, a full store URL, a Supervisor or add-on log line.

`02-07-SUMMARY.md` itself is written only in Task 23: execute-phase treats a plan with a SUMMARY as complete, so a
partial SUMMARY in the phase directory would let a restart skip the cleanup.

- **R1 Locate.** `E2E_SCRATCH` missing and no completed task reported by the orchestrator: this is the first session; create the directory and the empty files under `umask 077`, write `Status: in progress` and `## Evidence` into `summary-draft.md`, and continue at Task 1. `E2E_SCRATCH` missing although the orchestrator reports completed tasks: the run state is lost; run no host command and stop with a `checkpoint:decision` that lists the completed tasks and offers cleanup with fresh approvals (the store slug can be read again from the proxy's registration log line with the step B command).
- **R2 Check.** `grep -qsE '[0-9a-fA-F]{32}|https?://|github_pat_|ghp_' "$HOME/.local/state/mrp-e2e-02-07/e2e.env" "$HOME/.local/state/mrp-e2e-02-07/steps.log" "$HOME/.local/state/mrp-e2e-02-07/summary-draft.md"; test $? -eq 1` passes (exit status 1 means no match and no read error), and `cut -d= -f1 "$HOME/.local/state/mrp-e2e-02-07/e2e.env" | sort | uniq -d` prints nothing. On a failure: stop, name only the file, change nothing. The same check runs again after every write to `summary-draft.md`.
- **R3 Position.** Read `e2e.env`, `steps.log` and `summary-draft.md` in full (they are small), then log the checkpoint answer this session received, if any. Walk the tasks in plan order: a task with a terminal event (`confirmed`, `approved`, `aborted`, `skipped`, `done`, `failed`) is complete, and the first task without one is next. After an `aborted` or `failed` event, cleanup starts at the first task that applies: Task 16 when Task 10 was `started` or later (the test add-on may be installed), else Task 18 when Task 6 was `confirmed` (the options hold the test repository), else Task 21; the session that logs the `aborted`/`failed` event also logs `skipped` for every task the routing passes over. For Tasks 16, 19 and 22, `aborted` means pause: the next session presents the same checkpoint again. Because the position comes from the log, the cleanup tasks are reachable from every session.
- **R4 Continue.** Never repeat a host action of a task logged `done`, and never run a host command for a task whose approval checkpoint is not logged `approved`. An auto task logged `started` without `done` or `failed` was interrupted: present its approval checkpoint again, marked "resume after an interruption at {UTC of started}"; after a new `approved`, run the task's read-only state check first and skip every change that is already in effect (registered, installed, uninstalled, deleted), rewrite its block, then log `done`. Time limits (step B: 5 minutes from `restart_utc`; step D: `sync_interval` + 5 minutes from `push_utc`; step G: `sync_interval` + 2 minutes from `delete_utc`) count from the logged times, not from the resume.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| executor -> production host (`ha` over SSH) | Every command changes or reads a live Home Assistant installation |
| production host output -> repository files | `ha` output and logs can carry hostnames, URLs and names |
| user -> HA UI (options) | The GitHub token is entered only in the UI |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-34 | Elevation of privilege | unapproved host action by the executor | high | mitigate | `gate="blocking-human"` approval checkpoint before every host step; auto tasks carry a `<precondition>` on the approval; read-only queries named per step |
| T-02-35 | Denial of service | Core/Supervisor restart or manual reload during the run | high | mitigate | Never restart Core/Supervisor or run `ha store reload` (rules, prohibitions); only the proxy add-on is restarted, by the user in the UI |
| T-02-36 | Information disclosure | token on a command line or in shell history | high | mitigate | Options edited in the HA UI only (Pitfall 9); no `ha addons options` call; options never read |

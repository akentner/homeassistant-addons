<resume>
Resume protocol: the first step of every session. The executor returns at every checkpoint and execute-phase spawns a
fresh agent for the next task, so this plan runs as many short sessions, and nothing from an earlier shell survives.
Every session (the first one, each continuation, and a fresh start after a crash) runs R1-R4 before anything else and
runs no host or GitHub command before R4.

Run state lives only in `E2E_SCRATCH` = `$HOME/.local/state/mrp-e2e-02-07` (directory mode 0700, files mode 0600).
Shell variables do not persist between commands, so every command that needs a run state file spells out this path.

- `e2e.env`: run values as `key=value`, each key at most once (`repo` as account/name, `addon`, `delete_scope` (`yes`/`no`), `proxy_slug`, `store_slug`, `sync_interval`, `sub_install`, `restart_utc`, `push_utc`, `new_version`, `delete_utc`). A resumed step reuses an existing key and never appends a second line for it.
- `steps.log`: append-only, one line per event: `{UTC} task={N} event={confirmed|approved|aborted|skipped|started|done|failed}`. The session that receives a checkpoint answer logs it (`confirmed` for the human-action tasks, `approved`/`aborted`/`skipped` for approval checkpoints; for Task 26 `approved` = delete, `skipped` = keep). An auto task appends `started` right before its first host or GitHub write and `done` (or `failed`) only after its evidence block is written; Task 1 and Task 28 log `started`/`done` around their local work.
- `store-before.txt` (baseline slug list from step A), `needles` (Task 28), `test-repo/` (the working copy of the test repository, created in Task 1), and `summary-draft.md`: the partial SUMMARY, a `Status: in progress` line and one `### ...` block per step (`Precondition`, `Step A` to `Step H`, `Test repository`) with masked evidence; a re-run step replaces its block and never adds a second one.
- In the tasks below, "scratch file" means `e2e.env` and `steps.log`, and "record for the SUMMARY" means writing that step's block in `summary-draft.md`.
- Never in any run state file: a GitHub or other token, an access hash, a full store URL, a Supervisor or add-on log line.

`02-07-SUMMARY.md` itself appears only at the end of Task 28, after the run state is deleted: execute-phase treats a
plan with a SUMMARY as complete, so a partial SUMMARY in the phase directory would let a restart skip the cleanup, and
a run state that outlived the SUMMARY would never be cleaned up.

Walk the tasks in plan order: a task with a terminal event (`confirmed`, `approved`, `aborted`, `skipped`, `done`, `failed`) is complete, and the first task without one is next.

<objective>
Complete MRP-10 with rotation of the `local` user and a full leftover lifecycle: `mrp local rotate --yes` registers the
new URL first, then revokes the old URL at once and tries to remove the old store repository; a refusal leaves that
store repository as a reported leftover whose URL already answers 404; an interrupted rotation, a hand edit of
`access.json` and a hostname change are detected and reported, never deleted automatically.

Purpose: rotation of the `local` URL is the response to a leaked internal URL. D-09 requires add-first, report, never
force. D-11 (user decision 2026-11-18) requires the old URL to be revoked in the same rotation and a clear warning before
it: add-ons installed from the old store repository get no updates until they are reinstalled from the new one. D-28
fixes the registration value the rotation leaves behind (`registered`, or `leftover` after a refusal).
Output: rotate executor and rollback in `app/registration.py`, `mrp local rotate` with the warning and `--yes`, leftover
detection, tests.
</objective>

## Confirmed decisions and assumptions (for user confirmation)

Locked decisions implemented: D-09 (add first, then try to remove; refusal reported, never forced, never looped),
D-10 (leftover recorded and logged at warning), D-11 (user decision 2026-11-18, was Q-2: the old URL is revoked in the
same rotation, right after the add of the new one; warning before rotating; no flag that keeps the old URL serving),
D-28 (registration `registered` after a clean rotation, `leftover` while an old store repository is left).

Planner assumptions:

- **A-11 Rollback:** a failed add of the new URL rolls the rotation back; the old URL is never revoked before the new
  one is registered, and once the add succeeded it is revoked at once (D-11).
- **A-12 Leftover detection is report-only:** `interrupted` and `orphaned` leftovers are never deleted automatically,
  including after a hostname change (an add-on installed from the old URL may still exist). A retired `local.*` entry
  is revoked by the pass, because D-11 already decided that the old URL stops at rotation time.
- **A-18 Confirmation flag:** the D-11 warning is printed on every `mrp local rotate`; the rotation runs only with
  `--yes`. A flag instead of an interactive prompt, because `mrp` runs through `docker exec`, often without a TTY, and a
  flag is testable and scriptable. The sync process does not require a confirmation key in the request file; the Phase 3
  GUI asks its own confirmation before it writes the same request.

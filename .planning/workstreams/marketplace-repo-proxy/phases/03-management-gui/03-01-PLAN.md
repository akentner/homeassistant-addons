## Interface Phase 2 has to meet (D-19)

Phase 3's reader (`app/web/registration.py`) assumes this layout of `/data/supervisor.json`; the manager passes it to
the Phase 2 owner, and 03-01-SUMMARY.md repeats it under "Interface for Phase 2":

- A JSON object, written by Phase 2's single writer with atomic replace, mode 0600; Phase 3 reads it as root without a
  lock and never writes it.
- `repositories`: a list with one object per repository: `repository` = `owner/repo` (matched case-insensitively
  against the configured repositories), `registration` = one of `registered`, `missing`, `leftover`, `error`, and an
  optional `message` (text without a full access hash or URL; the GUI masks 32-hex runs anyway and shows at most 200
  characters).
- Every other top-level key and every other entry key is ignored. A missing or unreadable file, a repository without
  an entry and any other state value mean "no data" for that repository.
- Observation for the manager: Phase 2's current plans (02-01, 02-06) already use `repositories[].repository`,
  `registration` and `message`, but with the states `registered`, `pending`, `disabled`, `failed` and a separate
  `leftovers[]` list. Until Phase 2 writes D-19's four states into `registration`, the GUI shows no registration data
  (CONTEXT Q-1: whichever phase merges second aligns).

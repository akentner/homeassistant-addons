<objective>
Pin, with a test-only change, how a multi-line private key travels from a Bitwarden vault item to secrets.yaml, and
record in the test module docstring which Bitwarden item types can carry such a key at all.

Purpose: confirm that a PEM-style key in Login notes or a Login custom field survives
Provider.fetch() -> render_secrets -> yaml.safe_load -> write_secrets -> read_secrets byte-identical (newlines and the
trailing newline included), and document two findings that surprise users: Secure Notes (type 2) become files, never
secrets, and SSH-key items (type 5) are skipped and counted under the misleading "card/identity items skipped" notice.

NOT touched; the notice wording and the missing SSH-key docs rows are reported as a follow-up, not fixed here.
</objective>

    Start the module with an English docstring stating that the file pins how a multi-line private key travels from a
    Bitwarden item through Provider.fetch() and the writer into secrets.yaml, and that the key is fake and generated at
    runtime.

    Add a module-level helper `fake_private_key(seed: str = "fake-key") -> str` and a constant `KEY = fake_private_key()`.
    The helper keeps the marker label in a constant `LABEL = "OPENSSH PRIVATE KEY"` and assembles the first and last line
    with f-strings around `{LABEL}` (five dashes, then BEGIN or END, a space, the label, five dashes), so the contiguous
    BEGIN-plus-label text never appears as a literal in the source: that keeps secret scanners such as the repo's
    gitleaks hook quiet and makes plain that nothing here is a real credential. The body is
    `base64.b64encode(random.Random(seed).randbytes(400)).decode()` (536 characters), cut into 70-character lines (seven
    full lines plus one 46-character last line, like real OpenSSH output). Return the BEGIN line, a newline, the body
    lines joined by newlines, a newline, the END line and exactly one final newline. Never embed a real key and never
    read one from disk.

    Add two tests.

    First, `test_fake_key_is_multiline_wrapped_with_trailing_newline`: assert KEY starts with five dashes plus BEGIN and
    ends with five dashes plus a newline; the body (the lines between the first and the last marker line, i.e.
    `KEY.split("\n")[1:-2]`) has more than five lines, every line at most 70 characters, the first exactly 70 and the last
    shorter than 70 and non-empty. This guards the fixture, so the byte-identical assertions below stay meaningful.

    Second, the tracer `test_login_notes_key_roundtrips_fetch_to_yaml(fake_bw, bw_cfg)`: call
    `fake_bw.set_items` with one Login item whose only content is `name` "Deploy Host" and `notes` KEY (type 1, no login
    block needed). Run `Provider(bw_cfg).fetch()`. Assert `snap.secrets == {"deploy_host_notes": KEY}` and
    `snap.files == {}`. Render with `render_secrets(snap.secrets)`, parse with `yaml.safe_load`, and assert the loaded dict
    equals `snap.secrets`, `loaded["deploy_host_notes"] == KEY`, and that value still ends with the trailing newline.
    Finally assert `text.count("\n") == 1 + len(snap.secrets)`: the header line plus exactly one physical line per key,
    proving the multi-line value is stored escaped on a single YAML line rather than spread over several.

    This is the thinnest end-to-end path (fake bw subprocess -> Provider -> Snapshot -> writer text -> YAML parser) with
    real assertions, not a stub; Task 2 only adds more items and entry points on top of it.
  </action>

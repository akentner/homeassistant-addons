<objective>
Close the two security gaps that pre-commit can actually close in this repository — accidentally
committed secrets, and attack surface in the GitHub Actions workflows — and repair a hadolint
target that has been silently skipping seven of nine add-ons.

Purpose: the repo handles `SUPERVISOR_TOKEN`, `HA_TOKEN`, GHCR tokens, Cloudflare Access service
tokens and `MINIMAX_API_KEY`, and has no secret scanning at all. `actionlint` checks workflow
syntax and has no security rules, while `.github/workflows/opencode.yml` is comment-triggered
(`/oc`, `/opencode`) and hands a secret to a mutable action ref, and
`.github/workflows/_build-template.yml` interpolates `${{ inputs.* }}` straight into `run:`
blocks. Separately, `make docker-build-check` — the only place hadolint runs with the full
ruleset including DL3006 — iterates a hardcoded three-name list, one of which no longer exists,
so `coding-assistants` (several `curl | bash` installers, unpinned `latest` downloads) has never
been checked by it.

Output: two new pre-commit hooks that are proven to fire, two narrowly scoped config files, a
discovery-driven hadolint target, and a documentation section that says what is and is not
covered.
</objective>

<locked_decisions>
**D-01 — The gitleaks hook must be proven to fail before it is believed.** A hook that has only
ever printed `Passed` is not verified. Task 1 plants a control and asserts a non-zero exit.

**D-02 — Reuse the discovery idiom that already exists.** `docker-build-check` adopts the
`for addon_dir in */` + `config.yaml` guard from `validate-addons` (Makefile:75) and the same
notion of "an add-on is a top-level directory with a manifest" that `build.yml`'s `detect` job
uses. No new discovery mechanism is invented. This target additionally requires a `Dockerfile`,
because that is what it hands to hadolint.

**D-03 — `[extend] useDefault = true` is mandatory in `.gitleaks.toml`.** A `.gitleaks.toml`
carrying only allowlists REPLACES the built-in ruleset: every rule disappears and the hook keeps
printing `Passed`. This is the single most dangerous failure mode of this task. The negative
control therefore runs AFTER the config file exists, so it proves the config did not disarm the
scanner.

**D-04 — Path + rule scoped `[[allowlists]]`, one block per concern.** Chosen over the two
alternatives for stated reasons:

- _Inline `gitleaks:allow` comments_ — rejected. Would require editing five files including two
  GSD-managed `.planning/` documents, needs one comment per finding (eight edits that decay as the
  test suites grow), and cannot be placed inside `output_test.go`'s multi-line PEM string literal
  without changing the test payload.
- _Fingerprint allowlisting_ — rejected. A gitleaks fingerprint encodes a line number, and the
  fingerprint form differs between a `git` history scan and a `--staged` scan. Every edit above a
  finding invalidates the entry, so it cannot be verified once and trusted after.
- _Path + `targetRules`_ — chosen. The three Go files are dedicated redaction/scrubbing test
  suites whose entire purpose is to carry synthetic credential shapes, so the path IS the semantic
  boundary: any future synthetic shape added to them is a false positive by construction. Rule
  scoping via `targetRules` keeps every other rule live inside those same files.

A repo-wide `regexes` allowlist is forbidden. `^\.planning/` as a path is forbidden — the two
planning documents are allowlisted by their exact paths, so a future planning document containing
a real secret still trips.

**D-05 — `--offline` goes on the zizmor hook entry.** zizmor runs online audits whenever
`GH_TOKEN`, `GITHUB_TOKEN` or `ZIZMOR_GITHUB_TOKEN` is present in the environment. Because
`make check-all` → `lint` → `pre-commit run --all-files` reaches this hook, and Makefile:99-105
requires every `check-all` member to be offline and deterministic, the flag is not optional.

**D-06 — How zizmor findings may and may not be handled.** FORBIDDEN, in `zizmor.yml` or on the
hook entry: `--min-severity`, any `--persona` downgrade, a `remap` of severity, an `|| true`
wrapper or any other always-exit-zero shape, and `disable: true` for any audit other than the
`unpinned-uses` hash-pin requirement. Also FORBIDDEN: any edit to a file under `.github/`.
PERMITTED, and the expected outcome: one `rules.<audit-id>.ignore` entry per already-existing
finding, in the narrowest form zizmor accepts, each carrying a comment that names the audit and
marks it a deferral. That shape keeps `make check-all` green while leaving the hook blocking for
every NEW finding — which is the entire point of installing it. An always-zero hook would silence
the future as well as the present.

**D-07 — `unpinned-uses` is relaxed, not deleted, if zizmor allows it.** `docs/DEVELOPMENT.md`
lines 174-188 make floating-major refs (`@v7`, `@v4`, `@v6`) the deliberate policy and forbid SHA
pins. Try the narrowest expression of exactly that policy first; fall back to switching the audit
off only if zizmor 1.30.1 rejects the narrower form or still reports on floating-major refs.
Record which form shipped.

**D-08 — Neither SUMMARY.md nor any committed document may reproduce a synthetic credential
literal.** Refer to every finding by `path:line`, constant name and rule ID only. Two reasons: the
new hook scans the staged diff, so a SUMMARY.md quoting those literals would fail its own commit;
and pasting credential-shaped text into documentation is the habit that produced two of the eight
baseline findings in the first place.

**D-09 — Findings that cannot be fixed in scope are reported, never absorbed.** For hadolint on
the seven newly covered Dockerfiles: do not extend the `--ignore` list, do not edit a Dockerfile.
For zizmor: do not edit a workflow. In both cases the finding goes into SUMMARY.md verbatim as a
follow-up.
</locked_decisions>

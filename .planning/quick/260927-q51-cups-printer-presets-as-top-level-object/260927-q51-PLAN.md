# Quick Task: `printer_presets` as a Top-Level Object List

## Goal

Replace the just-shipped `printers[].presets` flattened-string config field (0.1.0-9/0.1.0-10) with a proper
object-based config: a NEW top-level `printer_presets` list of objects, each `{printer: str, name: str, options:
str}`, where `printer` is a foreign-key string matching one of the configured `printers[].name` values. This is a
deliberate, approved BREAKING CHANGE that replaces the old field entirely — no migration shim, no back-compat
read path.

**Why (user's own words, paraphrased):** the previous flattened-string format
(`"Name|Key=Value ...;Name2|Key=Value ..."`) already caused a real config mistake once — a stray literal `"`
character ended up inside the string when pasted into the HA UI's YAML editor, silently breaking one preset's
parsing. An object-based list gives individually validated `printer`/`name`/`options` fields per row instead of
one big delimited string a user can mistype.

**Why not `printers[].presets` as a nested list-of-objects (do not re-litigate — verified twice already this
session against https://developers.home-assistant.io/docs/add-ons/configuration/, which states verbatim: "Nested
arrays and dictionaries are supported with a maximum depth of two"):** `printers[]` is already a depth-two
list-of-objects (list → object with scalar fields); a `presets[]` list-of-objects nested inside one of its
entries would be a third level and cannot be expressed in the `schema:` block at all. The fix is to HOIST
presets to their own TOP-LEVEL list (`printer_presets[]`, a sibling of `printers[]`, not nested inside it) — a
top-level list of objects is only depth-two itself, so it is fully schema-valid, and gives a real, repeatable
list UI in the HA options form.

## Security Notes

This continues the same T-21-01 discipline already established in `cups/generate_config.py` (module docstring,
`LOCATION_RE`/`DRIVER_MODEL_RE`/`PRESET_NAME_RE`/`PRESET_OPTION_TOKEN_RE`). No new injection surface is
introduced by this change: `build_preset_injection_snippet()`'s validation logic (regex-match-or-skip, then
`shlex.quote()`/quoted-heredoc embedding) is byte-for-byte unchanged — only its INPUT SHAPE changes, from a
flattened string it used to parse itself to an already-split `list[tuple[str, str]]` the caller now provides.
`group_presets_by_printer()` never embeds `printer`/`name`/`options` into a shell string itself — it only builds
a Python dict keyed by `printer`, and the only place any of these values reaches generated shell text is still
`build_preset_injection_snippet()`'s existing, unchanged validate-before-embed gate. The new unmatched-FK WARNING
in `main()` interpolates `printer_name` only into an f-string `print()` call (via `!r`, i.e. `repr()`), never
into a shell command or file write — no new mitigation is needed for it.

   ```python
   def group_presets_by_printer(options: dict) -> dict[str, list[tuple[str, str]]]:
       """Group the top-level `printer_presets` option list by its `printer` FK.

       Reads `options.get("printer_presets") or []` and, for each entry,
       skips with a WARNING (mirroring this file's existing
       `if not isinstance(entry, dict):` skip pattern used for `printers[]`
       entries) when the entry itself is not a dict, or when
       `printer`/`name`/`options` are missing or not strings. Surviving
       entries are appended as `(str(entry["name"]), str(entry["options"]))`
       pairs into a dict keyed by `str(entry["printer"])`.

       Does NOT validate name/options against PRESET_NAME_RE/
       PRESET_OPTION_TOKEN_RE itself -- build_preset_injection_snippet()
       still does that per-pair validation exactly as before; this
       function's only job is grouping raw pairs by their `printer`
       foreign key. A `printer` value that does not match any CURRENTLY
       CONFIGURED printer name is not an error at grouping time -- this
       function has no visibility into which printer names are valid, it
       just groups by whatever string is there. build_printer_registration()
       naturally only ever looks up names it is actually iterating over, so
       an unmatched entry simply never gets consumed here -- main() surfaces
       a WARNING for that case separately (see main()'s own printer_presets
       FK check).
       """
       grouped: dict[str, list[tuple[str, str]]] = {}
       for entry in options.get("printer_presets") or []:
           if not isinstance(entry, dict):
               print(f"WARNING: skipping non-object printer_presets[] entry: {entry!r}", flush=True)
               continue
           printer = entry.get("printer")
           name = entry.get("name")
           preset_options = entry.get("options")
           if not isinstance(printer, str) or not isinstance(name, str) or not isinstance(preset_options, str):
               print(
                   f"WARNING: skipping printer_presets[] entry with missing/non-string "
                   f"printer/name/options: {entry!r}",
                   flush=True,
               )
               continue
           grouped.setdefault(printer, []).append((str(name), str(preset_options)))
       return grouped
   ```

   `printer_presets` (optional, default `[]`) is a TOP-LEVEL list of objects — a sibling of `printers`, not

   printer_presets:

   at every add-on start — idempotent across restarts, same as the rest of this add-on's generated
   configuration.

   stray literal `"` pasted into the HA UI's YAML editor silently broke one preset's parsing), and the new
   object-based list gives a real, individually validated list UI instead.

   micro-language caps nested list/dict depth at two (see the
   [add-on configuration docs](https://developers.home-assistant.io/docs/add-ons/configuration/)). `printers[]`

   nested inside one of its entries would be a third level and cannot be expressed in `schema:`. Hoisting
   presets to their own top-level list (`printer_presets[]`, a sibling of `printers[]`) keeps it at depth two
   itself (list → object with scalar `printer`/`name`/`options` fields), so it is fully schema-valid and gives a
   real, repeatable list UI in the HA options form — individually validated fields per row, not one big
   delimited string a user can mistype.
